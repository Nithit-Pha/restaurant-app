# Step 2 — Ingredient stock

Status: approved 2026-11-12 · Branch: `main`
Source: [ideas-dine-in-kitchen-stock.md](ideas-dine-in-kitchen-stock.md), Step 2.

## Goal

The app knows the ingredients in the shop. Orders reduce stock automatically
through a recipe per dish; a dish shows "sold out" when an ingredient runs out;
staff count stock and enter waste; the owner sees what is running low.

## Facts checked (2026-11-12)

- Orders become paid in two places: `changePayment` in
  `server/src/modules/orders/orders.service.ts` (pickup/delivery; completing a
  cash order marks it paid) and `payVisit` in
  `server/src/modules/dineIn/dineIn.service.ts` (table bill).
- PromptPay orders can be paid before cooking (dev DB: 7 orders `PAID` while
  still `PENDING`); dine-in tables pay at the end of the meal. "On payment" is
  therefore too early for one and too late for the other.
- "Sold out" today is the manual switch `MenuItem.isAvailable`.
- Live updates exist (`server/src/utils/events.ts`, Server-Sent Events); a
  `stock` event can be added.

## Decisions (approved)

| Decision | Choice |
| --- | --- |
| D1 When stock is reduced | When staff **accept** the order (status → `PREPARING`), in the same transaction. Cancelling an order puts its stock back once. Food that was really thrown away is entered as Waste. *Changes the earlier idea "on payment".* |
| D2 Stock in | "Stock in" button with an optional price; with a price it also creates a Finance `FOOD_SUPPLY` expense. |
| D3 Low-stock alert | Red counter on "Stock" in the admin menu plus a "Low stock" list, updated live. Bell, LINE and email come later with the shared alert system. |
| Negative stock | Allowed (the order is never blocked by a wrong count); shown in red; the next count fixes it. |
| Who does what | Owner (Super Admin): ingredients and recipes. Staff and owner: stock in, count, waste. The Permissions page comes later. |
| Way of working | One slice at a time: code + tests + commit, report, wait for OK before the next. |

## Data model (new migration)

- `Ingredient`: name, unit (kg, pcs, L …), quantity, reorderLevel, storage,
  isActive (deactivated, never deleted).
- `RecipeItem`: menuItemId + ingredientId + amount (per one dish).
- `StockMovement`: type `SALE | SALE_RETURN | PURCHASE | COUNT_ADJUST | WASTE`,
  change (+ in, − out), reason, userId, orderId?, createdAt.
- `Order.stockDeductedAt`: stock was reduced for this order (never twice;
  put back exactly once on cancel).

## Slices (in this order)

### 2a — Ingredients and stock page
- DB: `Ingredient`, `StockMovement` (+ enum).
- Server: `server/src/modules/stock/` — list/create/update ingredients (Super
  Admin); stock in (with optional `FOOD_SUPPLY` expense), count, waste (Staff +
  Super Admin); movement history. Every change in the audit log.
- Client: `/admin/stock` page (ingredients table, stock in / count / waste
  dialogs, history); "Stock" in the admin menu. API calls in a separate
  `client/src/api/stockApi.ts`.

### 2b — Recipes and automatic reduction
- DB: `RecipeItem`, `Order.stockDeductedAt`.
- Server: recipe per menu item; pure `planStockMoves()` (unit-tested);
  reduction when an order moves to `PREPARING`, putting back on `CANCELLED`.
- Client: "Recipe" section for a menu item.

### 2c — Sold out and low stock
- Server: menu marks a dish sold out when an ingredient does not cover one
  portion; placing an order with such a dish is refused; `stock` live event.
- Client: "Sold out" on the menu; low-stock counter on "Stock" and a
  "Low stock" list.

## Tests

- Vitest: stock move planning (reduce, put back, never twice), sold-out rule,
  count and waste.
- Playwright: ingredient + recipe → order → accept → stock lower; stock used up
  → dish sold out and cannot be ordered.

## Not in Step 2 (later)

- Recipes for options (e.g. "extra egg").
- Cost price of a dish calculated from its recipe.
- Permissions page; suppliers and purchase orders (Step 3); bell / LINE /
  email alerts (shared alert system).

## Risks

- Real stock drifts from the app; regular counts fix it.
- Another session was working on `main` at the same time (orders service,
  API slice). Stock code stays in its own files where possible; shared files
  (`orders.service.ts`, `dineIn.service.ts`) only get small hooks in 2b.
